# Хуки в рабочем пространстве

`POST /hooks/{hookId}` запускает сохранённую задачу агента от имени владельца хука без открытого чата. Агент использует настройки, инструменты, скиллы и каналы владельца; промпт задаёт задачу и место доставки результата. Полезная нагрузка не получает отдельного ограничения прав: используйте доверенные события; изоляция полномочий хука описана в [#817](https://github.com/D00mch/souz/issues/817). Поддерживаются LOCAL и DOCKER, **один процесс backend**. Core-тулы `hook.create/get/list/update/delete` управляют хуками; расписания используют отдельный JobService.

## Core-инструменты

Категория `HOOKS` содержит `hook.create`, `hook.get`, `hook.list`, `hook.update`,
`hook.delete`. Они доступны через обычные Skill discovery и `RunSkillCommand`
с учётом `enabledTools`; владелец всегда берётся из контекста выполнения.

| Тул | Вход |
|---|---|
| `create` | `prompt`; необязательно `hookId`, `bearerToken`, `enabled` (по умолчанию true) |
| `get` | `hookId` |
| `list` | без параметров; включает выключенные хуки |
| `update` | `hookId`, `expectedRevision`, непустой набор `prompt`/`bearerToken`/`enabled` |
| `delete` | `hookId`, `expectedRevision`; отсутствие хука идемпотентно |

Для создания задайте `SOUZ_HOOK_PUBLIC_BASE_URL`, например
`https://example.com/souz`. Это доверенная внешняя HTTPS-база без query/fragment;
результат содержит полный URL `/hooks/{hookId}` и структуру JSON/multipart запроса.
Приём по существующим адресам не требует этой настройки. Allowlist владельцев
остаётся обязательным. Prompt должен содержать весь контекст условия, разрешённое
действие и назначение: итог в техническом чате сам по себе не уведомляет пользователя.

Без `bearerToken` create генерирует случайный секрет и возвращает его только в
этом ответе (`auth.token`); get/list его не возвращают. YAML хранит SHA-256.
Если ответ потерян, прочитайте хук и явно замените токен через update.
Для композитных интеграций заранее сохраните секрет в закрытом состоянии Skill и
передайте его вместе со стабильным `hookId`: точный повтор create с тем же
определением/секретом возвращает `created=false`. Переданный секрет не возвращается.
Не показывайте credentials в обычных ответах пользователю.

`get/list` возвращают revision для проверки конкурентных изменений; update/delete
требуют её точного совпадения. Операции проверяют исходный файл перед дальнейшей
записью и используют атомарную замену с reload. Delete сначала выключает хук;
квитанции и история сохраняются, уже запущенные агенты не прерываются.
`status=succeeded` подтверждает операцию; при `partial` сначала проверьте состояние,
а не повторяйте создание вслепую. Секретные ошибки и содержимое YAML не возвращаются.

[Skill сценариев с камерой](camera-scenarios.md) связывает эти общие тулы с MCP
детектора; формат хука не содержит camera-specific полей.

## Настройка и reload

Задайте `SOUZ_HOOK_OWNERS=user-42,user-43` или `souz.hooks.owners`. Пустой список отключает хуки. Пользователи должны существовать: YAML не создаёт учётные записи.

Создайте `<workspace>/hooks/<name>/hook.yaml`:

```yaml
version: 1
hookId: sample-123
ownerUserId: user-42
enabled: true
auth:
  type: bearer
  tokenSha256: "REPLACE_WITH_SHA256_OF_RANDOM_SECRET"
prompt: |
  Обработай событие и отправь результат в мой Telegram.
  Если канал недоступен, объясни это в результате выполнения.
```

Сгенерируйте секрет, например `openssl rand -hex 32`; в YAML храните только SHA-256. Bearer-токен содержит 32–512 символов без пробелов. Храните исходный токен в закрытой конфигурации клиента, вне Git, URL и промптов.

LOCAL читает общее настроенное workspace: файлы здесь — доверенная конфигурация оператора, без изоляции владельцев. DOCKER читает workspace соответствующего пользователя и требует совпадения `ownerUserId`. См. [контракт sandbox](../sharedLogic/docs/runtime-sandbox-and-skills.md).

Читаются только `hooks/*/hook.yaml`. Неизвестные поля, небезопасные пути, некорректные хеши и сочетание `auth` с `verify` отклоняются. В LOCAL определения с другим явно указанным владельцем пропускаются до проверки остальных полей. Некорректный файл отключает загружаемый набор владельца; конфликт ID отключает все определения с этим ID. Диагностика не включает содержимое YAML.

Определения загружаются при запуске. `POST /v1/hooks/reload` через доверенный прокси перечитывает файлы владельца и возвращает `hookIds`. Смена токена, кода verifier и параметров применяется после reload. Удаление определения или `enabled: false` прекращает приём и обработку очереди. Изменение промпта или verifier отменяет ожидающие события предыдущей версии. Уже запущенную работу отменяют через API выполнения.

## Проверяющая команда

Вместо `auth` можно указать:

```yaml
verify:
  runtime: PYTHON
  script: scripts/verify.py
  parameters:
    audience: "https://your-host.example/hooks/sample-123"
```

Verifier запускается через `SandboxCommandExecutor` в LOCAL/DOCKER-среде владельца до создания квитанции, выбора Skill или обращения к LLM. Отдельный контейнер не создаётся. Это доверенный код с обычным доступом среды к файлам, сети и окружению; `python3` и библиотеки должны быть установлены в ней.

При загрузке сохраняется снимок каталога хука без `hook.yaml`: не более 64 файлов и каталогов, 1 МиБ суммарно, глубина до 8 компонентов. Симлинки запрещены. Относительные пути допускают буквы ASCII, цифры, `_`, `-`, `.`; компоненты `.` и `..` запрещены. `parameters` — JSON-объект до 8 КиБ.

Снимок копируется в `.hook-verifier-<uuid>` внутри workspace. Это рабочий каталог команды; после завершения или отмены он удаляется. Авария процесса backend может оставить каталог, но он не используется повторно. Постоянное состояние интеграции храните отдельно.

В stdin передаётся JSON:

```json
{"version":1,"method":"POST","path":"/hooks/sample-123","headers":{"authorization":["Bearer provider-token"]},"bodyBase64":"e30=","parameters":{"audience":"https://your-host.example/hooks/sample-123"},"checkedAt":"2026-09-24T18:00:00Z"}
```

`path` отражает путь после nginx; ожидаемый адрес берите из `parameters`. Заголовки приведены к нижнему регистру, значения сохранены списками; `Host`, `X-User-Id`, `X-Souz-Proxy-Auth` исключены. Допускается до 32 имён и 16 384 символов. Подпись проверяйте по исходным байтам `bodyBase64`.

Код завершения — `0`, stdout — ровно один JSON-объект:

```json
{"accept":false}
```

либо:

```json
{"accept":true,"eventId":"provider-event-123","payload":{"message":"new event"}}
```

При успехе обязателен `eventId`: 1–200 символов без управляющих, не пустой и не состоящий из пробелов. `payload` необязателен; без него исходное тело должно быть UTF-8 JSON. Лишние поля, дубли ключей и посторонний вывод отклоняются. Нормализованные данные остаются недоверенными; заголовки и параметры не передаются модели.

По умолчанию владелец имеет два общих слота приёма и проверки; reload не сбрасывает занятые слоты. Тайм-аут проверки — 5 секунд, stdout — до 64 КиБ. Используются механизмы отмены, завершения процессов и ограничения вывода sandbox. Отказ возвращает `401`; ошибка, тайм-аут или некорректный stdout — `503`. Stderr не включается в ответ и логи хука. Reload во время проверки делает её старый результат непригодным для приёма.

## HTTP и выполнение

Для Bearer-хука передайте `Content-Type: application/json`, `Authorization: Bearer <secret>` и JSON-тело до 64 КиБ. Необязательный `Idempotency-Key` имеет те же ограничения формы, что `eventId`. Для verifier допускаются произвольные исходные байты до 64 КиБ; ключ берётся из проверенного `eventId`, а `Idempotency-Key` игнорируется.

### Вложения Bearer-хука

Bearer-хук принимает `multipart/form-data`: одно текстовое поле `payload` с JSON до 65 536 UTF-8 байт и от одного до пяти файлов в повторяемом поле `files`. Общий размер тела, включая MIME-разметку, ограничен 10 000 000 байт; чтение тела — 15 секундами. Пустые файлы, лишние поля и повторное поле `payload` отклоняются. Multipart не поддерживается Python verifier: ответ `415 hook_multipart_requires_bearer`.

```bash
curl "$BASE_URL/hooks/$HOOK_ID" \
  -H "Authorization: Bearer $HOOK_TOKEN" \
  -H "Idempotency-Key: camera-event-123" \
  -F 'payload={"camera_id":"living_room","timestamp":"2026-11-07T12:00:00Z"}' \
  -F 'files=@frame-1.jpg' \
  -F 'files=@frame-2.jpg'
```

Нужно настроенное [файловое хранилище](../backend/docs/s3-storage.md); без него multipart возвращает `503 hook_attachments_unavailable`. Файлы сохраняются от имени владельца хука, MIME определяется по байтам. Изображения получают presentation `image`, остальные файлы — `document`. Действуют лимит размера файла и срок хранения этого хранилища. JSON события остаётся отдельными недоверенными данными; файлы передаются штатному агентному выполнению как вложения, изображения обрабатываются существующим [vision-механизмом](../backend/docs/attachments.md).

Квитанция сохраняет упорядоченные ссылки на файлы до `202`; очередь читает их из PostgreSQL. Ключ дедупликации учитывает JSON, нормализованные имена, порядок и содержимое файлов, независимо от MIME boundary. Повтор возвращает прежнюю квитанцию даже после истечения файлов; изменение данных под тем же ключом даёт `409`. Без ключа каждый запрос создаёт отдельное событие. Одновременный повтор во время загрузки может получить `503 hook_attachment_not_ready`; повторите с тем же ключом и данными. Не повторяйте действие по тайм-ауту его исполнения.

S3-загрузка предшествует транзакции приёма события. При последующем отказе или частичном сбое уже сохранённые файлы остаются до штатного удаления по retention; `202` выдаётся только после успешного сохранения файлов и квитанции. Ссылки и метаданные дополнительно проверяются на владение и срок доступности при приёме и запуске агента.

| Ответ | Значение |
|---|---|
| `202` | Квитанция записана в PostgreSQL; работа выполняется асинхронно |
| `200` | Повтор события: прежняя квитанция, без нового выполнения |
| `400`, `408`, `413` | Некорректный запрос, тайм-аут чтения, превышение размера |
| `401`, `404` | Отказ авторизации или недоступный ID |
| `409` | Ключ уже использован с другим телом или владельцем |
| `429` | Лимит приёма, проверок, очереди или событий за сутки |
| `503` | Хук отключён/изменён, хранилище или verifier недоступны |

Успешный ответ содержит `receiptId` и `duplicate`. Bearer проверяется до разбора тела; обе схемы авторизации работают до квитанции и LLM. Дедупликация сравнивает точный UTF-8 JSON: для Bearer — тело, для verifier — нормализованный `payload` либо исходное тело. Без ключа каждый Bearer-запрос создаёт событие. Ошибка выполнения не освобождает ключ.

`GET /v1/hooks/receipts/{receiptId}` через доверенный прокси возвращает владельцу статус, выполнение с `chatId`, итоговый текст, ошибку, число вызовов LLM и сообщённый расход токенов. Для событий, ответов на опции и отмены используйте существующие API выполнения. Успех агента сам по себе не подтверждает доставку сообщения: проверяйте результат инструмента отправки.

Каждое новое событие получает отдельный технический чат, скрытый из списка чатов. События одного хука последовательны; разные хуки разделяют лимит выполняющихся агентов. Ожидание опции освобождает слот, но удерживает очередь хука и бюджет события; продолжение снова занимает слот.

После перезапуска очередь продолжается, `waiting_option` сохраняется. Прерванная работа завершается ошибкой либо отменой с соответствующим долговечным событием. Завершённые состояния сохраняются, отсутствующие терминальные события восстанавливаются без дублей. Внешние эффекты с неизвестным результатом автоматически не повторяются.

## Лимиты и публикация

Значения заданы в [HookConfig](../backend/src/main/kotlin/ru/souz/backend/hooks/HookDefinitions.kt). Ограничены очередь, события владельца за сутки, параллелизм, длительность запуска, вызовы LLM на событие и владельца за сутки UTC. Попытки резервируются транзакционно **до** вызова, включая retries, вложенные инструменты и продолжения; перезапуск не сбрасывает бюджет. Дополнительно действуют минутные квоты запросов и сообщённых токенов, параллелизм провайдера. JSON-запрос к LLM ограничен 128 КиБ без содержимого штатных inline PNG; сами PNG data URLs имеют отдельный суммарный предел 14 000 000 UTF-8 байт на запрос. Текст, схемы инструментов и остальные attachment references входят в прежний предел 128 КиБ. Ответ ограничивается 4096 токенами при поддержке провайдером; меньшие настройки summarization сохраняются. Это не фиксированный денежный потолок.

Маршрут ограничивает размер и время чтения тела, а параллелизм приёма и проверок — отдельно для каждого владельца. Bearer проверяется до занятия слота; медленный запрос одного владельца не занимает слоты другого. Ограничение частоты по IP настройте на ingress. Публикуйте через TLS. Для `/v1/hooks/**` сохраняйте обычную авторизацию прокси; для входящих хуков передавайте только авторизацию самого хука:

```nginx
location /hooks/ {
    auth_basic off;
    client_max_body_size 10000000;
    client_body_timeout 15s;
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Souz-Proxy-Auth "";
    proxy_set_header X-User-Id "";
}
```

Для префикса `/souz` используйте `location /souz/hooks/` и `proxy_pass http://127.0.0.1:8080/hooks/;`.

## Проверка

`./gradlew :backend:test` требует Docker и локальный Python (`python3`, на Windows — `python`): проверяются рабочая сборка backend с PostgreSQL, авторизация, снимки verifier, дедупликация, доставка, очереди, бюджеты, опции и восстановление. Отдельные проверки протокола verifier и очистки процессов: `./gradlew :backend:test --tests 'ru.souz.backend.hooks.HookVerifierTest'`. Также выполните `./gradlew souzGateFast` и принятую проверку дублирования.
