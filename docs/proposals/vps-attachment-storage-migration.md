# План перехода VPS на общую S3-корзину

**Статус: установлен на VPS; ручная приёмка ожидается.** Backend собран из `codex/upstream-fork-sync-20261016`, коммит `ef61e781a32587c39bd266b5485bce117260ce21`. На VPS применяется [контракт хранения](../s3-storage.md) с одной приватной корзиной `souz-attachments-shared` и отдельным аккаунтом только для операций с объектами.

Проверенное состояние установки:

- Backend Flyway V1–V24; JobService V1–V3. Архивные поля hooks и отображение `attachment_buckets` сохранены.
- 39 файлов, 17 840 632 байта; SHA-256, MIME и метаданные проверены. Чтение через backend, запрет чужого владельца, новая запись, повторная запись и TTL проверены.
- Два действующих расписания перенесены в JobService с исходными cron, временем следующего запуска и `Europe/Moscow`; 51 завершённая запись сохранена в архиве. Старый планировщик Orion отключён, связанные старые hooks отключены.
- Все 34 банка Hindsight и их настройки сохранены. 14 runtime-контейнеров используют образ из ветки с прежними пользовательскими mounts; 14 именованных моделей доступны.
- Бэкапы, скрипты, манифесты и отчёты находятся в закрытом `/opt/souz-migration/20261016-upstream-ef61e781`; независимая копия сохранена на машине оператора. Проверенная база для отката — `souz_rollback_20261016`. Старые пакеты, образы, контейнеры и S3-бакеты сохраняются до завершения приёмки.

Инструкции ниже описывают подготовку перехода с исходной схемы и условия восстановления. Публичная запись и поллеры включены; восстановление старого бэкапа требует предварительного сохранения и согласования изменений после обновления.

## Подготовка до окна установки

- Зафиксировать версии backend, runtime-образа, конфигурации и Flyway history установленной базы. Снять инвентарь `attachment_buckets` и `stored_attachments`: user ID, file UUID, исходный бакет, ключ, размер, MIME, SHA-256, состояния и сроки. Проверить реальные имена и ограничения таблиц по установленной схеме.
- Зафиксировать связи файлов с сообщениями, delivery receipts, media operations и сессиями агента. Идентификаторы файлов, source keys и версии сессий сохранить; новая запись или повторное `save` не подходят, поскольку сбрасывают срок хранения и могут нарушить дедупликацию.
- Оператор создаёт общую приватную корзину и отдельный сервисный аккаунт с `GetObject`, `PutObject`, `DeleteObject`. Проверить запрет anonymous GET. Доступ к старым бакетам и административные права использовать только в миграторе, не в backend или Skills.
- Подготовить отдельный возобновляемый мигратор с режимом dry-run и manifest без секретов. Отображение: `(старый бакет, files/<file UUID>)` → `files/<sha256(UTF-8 user ID)>/<file UUID>`. Копировать с исходными MIME/метаданными; существующий целевой объект принимать только при совпадении размера и SHA-256, иначе останавливать переход. ETag не заменяет SHA-256.
- Согласовать SQL-переход по итоговой схеме интеграционной ветки. Для сохранённых таблиц нужны ALTER/проверки ограничений, а не повторные CREATE TABLE. `stored_attachments.user_id` не должен каскадно зависеть от локального `users`; очистка не должна удалять файлы из-за отсутствия такой строки. Индексы очистки должны соответствовать целевой миграции.
- Согласовать номера и checksums Flyway по точному списку установленной и целевой схем. В интеграционной ветке персонажность занимает V19, storage — V20, message attachments — V21, delivery parts — V22, media operations — V23, voice memory routing — V24. Старые номера V16–V21 пересекаются с апстримом; сверить итоговый список с конкретным SHA устанавливаемой ветки. Нельзя применять blanket `repair` или просто переименовать все history rows: сперва проверить соответствие SQL и схем, затем выполнить подготовленное согласование history транзакционно.
- Проверить переход на копии базы и копии объектов: все доступные файлы читаются новым backend, чужие file IDs отвергаются, expired/pending/deleting состояния сохраняют смысл, повторный запуск мигратора безопасен. Измерить объём и длительность, определить окно простоя и срок хранения резервных копий.

Ориентир для сверки существующей fork-схемы; это не готовая команда изменения Flyway history:

| Старая миграция форка | Целевая миграция | Проверка перехода |
| --- | --- | --- |
| V16 user personality | V19 user personality | Сверить колонки и checksum; сохранить prompt/revision |
| V17 attachments | V20 attachment storage | SQL-мост: убрать зависимость от attachment_buckets, сохранить IDs/TTL, согласовать индексы |
| V18 message attachments | V21 message attachments | Сохранить ссылки и проверить совпадение SQL |
| V19 attachment delivery parts | V22 attachment delivery parts | Сохранить receipts, включая неизвестные исходы |
| V20 attachment media operations | V23 attachment media operations | Снять legacy FK на attachment_buckets, сохранить claims |
| V21 voice memory routing | V24 voice memory routing | Сохранить voice_embedding_id, target_banks и delivered_banks; сверить SQL/checksum |

Миграции апстрима V16–V18 проверяются отдельно по фактической схеме; перенумерация fork-строк не заменяет применение их изменений.

Для голосовой памяти сохранить существующий household bank `userId`, персональные `person:<userId>:<embeddingId>` и их данные в Hindsight; исторические факты между банками не перераспределять. Перед установкой проверить `HINDSIGHT_API_URL`, `JEV_TOKEN` и поддерживаемую extraction mission с маркерами CONTEXT ONLY/NEW. Настройка и backup внешнего Hindsight входят в подготовку установки; backend не меняет конфигурацию банков. Проверить переключение спикеров и поиск личных фактов после установки.

Операционные мигратор и SQL-мост сохранены вместе с отчётами репетиции на восстановленной копии VPS. SQL-переход проверяет точный набор исходных версий и checksums и выполняется транзакционно; повторная проверка целевой истории не меняет данные. Мигратор объектов проверяет существующие копии и не удаляет источники. Эти скрипты относятся к конкретной установленной схеме; повторное применение требует сверки инвентаря. Чтение/запись старой и новой схем одновременно и автоматический fallback на старые бакеты не предусмотрены.

## Окно установки

1. Остановить backend и все его реплики/поллеры/cleanup workers. Отключить входящие записи и запуски, включая внешнее расписание Orion. Дождаться завершения или явно зафиксировать прерванные uploads и неизвестные результаты доставки. Не повторять такие внешние операции автоматически.
2. Снять согласованный backup PostgreSQL, конфигурации, старой программы/образа и `/souz` рабочих каталогов. Сохранить старые бакеты и экспорт manifest. Проверить возможность восстановления.
3. Повторить инвентаризацию без конкурентных записей. Скопировать необходимые объекты, проверить размер и SHA-256 чтением целевой копии; отдельно проверить все сохранившиеся файлы transcript/generated results. Для уже удалённых tombstones не восстанавливать содержимое. Неполные uploads и retryable deletions обработать по manifest, сохранив cleanup intent.
4. Выполнить проверенный SQL-мост и согласование Flyway history. Сохранить UUID, внешние user IDs, SHA-256, source keys, stored/expiry timestamps, сообщения, сессии и receipts. Старую `attachment_buckets` оставить как архив отображения до закрытия отката; runtime её не использует. Не создавать локальных пользователей ради старых файлов.
5. Установить подготовленный backend, задать `SOUZ_ATTACHMENTS_S3_BUCKET`, убрать `SOUZ_ATTACHMENTS_BUCKET_PREFIX`, сохранить server-only credentials. Для vision routes заменить legacy connection ID на публичное имя модели в `PROVIDER:modelName:modelId`; встроенные Codex routes с пустым именем не меняются. Пересоздать runtime-контейнеры с прежними bind mounts после сборки нового образа.
6. Запустить backend при закрытом входящем трафике. Проверить Flyway, health, доступ к старым файлам разных пользователей, отказ чужому пользователю, PrepareAttachment, изображение в модели, TG/VK download/upload, сохранённые сессии и дедупликацию. Отдельно проверить сроки хранения и cleanup на подготовленных тестовых объектах. STT/TTS и генерацию изображений проверять только с настроенными провайдерами.
7. Открыть приём запросов после проверки, записать фактические версии и итоговый manifest. Активные расписания Orion переносятся отдельным проверенным SQL-шагом; повторный импорт сверяет существующие записи и не создаёт дубликатов. Сохраняются инструкции и назначения доставки; для действий без уведомлений используются `requiresDelivery=false` и `atMostOnce=true`.

## Откат и завершение

До открытия записей: остановить новый backend, восстановить согласованный backup БД/конфигурации/образа и вернуться к старым бакетам. Скопированные целевые объекты этому не мешают.

После открытия записей простой возврат старой программы небезопасен: новые файлы находятся в общей корзине, изменились migration history и ссылки. Нужен отдельный обратный перенос новых объектов/метаданных либо восстановление backup с явно согласованной потерей изменений после окна. По возможности выявить ошибки до открытия трафика.

Старые бакеты не удалять автоматически. Удаление допустимо после окончания согласованного срока отката, проверки полноты manifest и подтверждения сохранности необходимых backup. До удаления отдельно проверить действующие retention/lifecycle policies старых бакетов, чтобы они не уничтожили резервные объекты раньше согласованного срока.
