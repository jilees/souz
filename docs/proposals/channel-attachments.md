# Вложения в Telegram и VK: решения и план реализации

**Статус: PROPOSED — целевой план; реализация и приёмка частичные.**

Дата: 2026-10-13. Документ фиксирует согласованные продуктовые границы и принятые стартовые решения для реализации. **Этап 0 закрыт; реализация выполняется.** Действующее поведение описано в [руководстве по вложениям](../channel-attachments.md). Полный объём этапов ниже ещё не принят и не включён в production. Он не описывает действующий публичный API и не разрешает считать перечисленные возможности реализованными. Имена будущих типов и операций ниже — рабочие обозначения, а не утверждённые wire-схемы.

## 1. Согласованные решения

1. Вложения поддерживаются в **backend Telegram и VK**: входящие текстовые документы, HTML, Markdown, PDF, изображения, аудио/голосовые; исходящие документы, изображения и голосовые.
2. **WebSocket колонок остаётся текстовым**, с внешними STT/TTS. Загрузка файлов, бинарные WS-сообщения, клиентские превью и изменение схем в `docs/public-souz-contract/` не входят в работу.
3. Desktop-функциональность не расширяется. Существующий desktop-код обработки файлов и голосовых служит источником для переиспользования через общие модули, без зависимости backend от desktop.
4. Изображения прежде всего передаются **основной модели непосредственно с вопросом и контекстом**. Базовая Sol ожидается способной понимать изображения; возможность должна быть подтверждена через фактически используемые модель, подключение и адаптер.
5. Допускается отдельная настроенная vision-модель для основной модели без поддержки изображений. Общая система автоматического выбора провайдеров не требуется.
6. **HTML и MD генерирует сама модель**. Файловые инструменты сохраняют содержимое; общий механизм вложений прикрепляет результат. Обязательный специализированный Skill для их создания не нужен.
7. **Генерация PDF выполняется Skill** с подготовленными зависимостями, рендером и проверкой результата.
8. Долговременное хранение — **одна приватная S3-корзина на окружение**, созданная оператором. Объекты сгруппированы по хешу пользователя, а доступ проверяется через owner-scoped метаданные PostgreSQL; см. [контракт хранения](../s3-storage.md).
9. PostgreSQL хранит принадлежность, метаданные, связи с сообщениями и состояние обработки/доставки. Docker sandbox остаётся рабочей областью для копий и промежуточных результатов.
10. По возможности не добавляются новые способы чтения/записи файловой системы. Подготовка рабочих файлов использует существующий `SandboxFileSystem`; отдельные host-path операции в канальных и S3-адаптерах не вводятся.
11. Создание файла и включение его в ответ — разные действия. Отправляются явно выбранные результаты, а не все файлы рабочей директории или пути, найденные в тексте ответа.
12. Используется **существующий S3-сервис на своей инфраструктуре**. На VPS подтверждён работающий MinIO; новый S3-сервис в рамках проекта не разворачивается. Приватная общая корзина вложений создаётся оператором отдельно от корзин существующих Skills.
13. Для первой версии срок хранения файлов — **30 дней с момента сохранения**, независимо от наличия ссылок в чатах. Подсчёт ссылок и продление срока при чтении/пересылке не нужны. После истечения срока история явно сообщает, что файл недоступен.
14. **TTS использует существующий локальный HTTP-эндпоинт эмулятора Orion**, выбранный пользователем по интеграции с OpenClaw: `POST /v1/audio/speech`, модель `orion-tts`. «Локальный» обозначает точку интеграции; эмулятор выполняет сам синтез через Sber. Своя TTS-модель, подбор CPU/GPU и прямая интеграция Союза с другим облачным TTS не требуются. Другой провайдер не используется как скрытый fallback.
15. **Внешние API для STT и генерации изображений допустимы; приоритет — максимально использовать провайдер CODEX.** Анализ изображений, работа с текстом документов и управление инструментами остаются у основной Sol. Доступ к специализированным media API не выводится из наличия Codex-авторизации. Стартовая схема подключений и её доказанные границы описаны в 4.9.
16. **Техническая основа раздела 8 принята как стартовая:** расширение текстовых контрактов ссылками на файлы/изображения, узкий host SPI, две файловые операции, AWS SDK v2, PDFBox/WeasyPrint, Tesseract, ZXing, ffmpeg и конфигурируемые лимиты. Незавершённые загрузки очищаются через 24 часа. Это согласование плана, без разрешения начать реализацию.

## 2. Объём и пользовательские сценарии

### Входит

- Получить файл без сопроводительного текста или текст с одним/несколькими вложениями.
- Разобрать TXT/MD/HTML, читать PDF по страницам, работать со сканами и визуальным содержимым страниц.
- Ответить на вопрос об изображении, прочитать надпись, декодировать QR, предложить идентификацию фильма по кадру с учётом неопределённости результата.
- Расшифровать голосовое и выполнить содержащийся в нём запрос; сохранить оригинал и расшифровку отдельно.
- Создать и отправить HTML/MD/PDF, сгенерированное изображение или синтезированное голосовое.
- Вернуться к вложению из предыдущего хода в пределах 30-дневного срока хранения, в том числе после восстановления runtime или пересоздания контейнера.
- Переслать выбранное вложение в другой принадлежащий пользователю TG/VK-канал через общий механизм channel delivery.
- Сохранить доступ к файловым результатам после выполнения Skill, composite-команды и субагента.

### Не входит

- Новые возможности desktop UI и публичного WS-клиента, файловый менеджер «Мои документы».
- Публичный файловый HTTP API, публичный хостинг сгенерированных HTML-страниц и публикация сайтов.
- Подключение S3 как смонтированной файловой системы, синхронизация всего sandbox с S3.
- Прямой аудиовход chat-модели, realtime-аудиодиалог, видеоанализ, клонирование голоса.
- Поддержка всех LLM-провайдеров во всех модальностях в первой поставке.
- Рефакторинг системы виртуализации или введение новых production project dependencies между модулями.

## 4. Предлагаемая архитектура

### 4.1. Три разных представления файла

- **Сохранённый файл:** стабильный ID, владелец, имя, проверенный MIME, размер, checksum и внутреннее местоположение в S3. Для созданного результата фиксируется конкретная версия байтов.
- **Вложение сообщения:** ссылка на сохранённый файл, порядок, способ показа (`document`, `image`, `voice`, `audio`), происхождение и связь с сообщением/чатом. MIME не определяет способ показа полностью: одно аудио можно отправить как документ или голосовое.
- **Представление для обработки:** рабочий sandbox-путь, извлечённый текст, расшифровка, изображение страницы, уменьшенная копия или provider upload handle. Производные данные связаны с оригиналом; их потеря не означает потерю оригинала.

История содержит стабильные ссылки. Временные URL, provider file IDs и локальные пути не являются долговременной идентичностью вложения. Восстановление запроса к LLM разрешает ссылку заново для выбранного подключения.

Размещение нейтральных типов следует минимальной схеме раздела 8: LLM content parts — в `:llms`, контракты файловых результатов/доступа со стороны агента — в `:agent`, продуктовые записи и S3-метаданные — в `:backend`. Не переносить bucket/key или S3 SDK в `:llms`.

### 4.2. S3, PostgreSQL и рабочая область

| Компонент | Ответственность |
| --- | --- |
| Общая приватная S3-корзина | Неизменяемые оригиналы и опубликованные в переписку результаты; при необходимости сохраняемые производные файлы. |
| PostgreSQL | Принадлежность файла внешнему пользователю; файловые записи; связи с сообщениями; готовность объекта; обработка и доставка. |
| Sandbox | Рабочие копии, редактирование, запуск Skills, рендер и промежуточные файлы. |

Предлагается backend-owned S3-доступ: backend использует настроенную корзину и проверяет принадлежность файла по доверенной identity, а не по аргументу модели. Ни модель, ни Skill не получают постоянные S3 credentials. S3-объекты приватны; временный доступ внешнего провайдера, если он нужен, ограничивается конкретным объектом и временем и не сохраняется в истории/аудите как постоянная ссылка.

Используется существующий MinIO на инфраструктуре проекта. Read-only проверка VPS подтвердила работающий контейнер MinIO и его S3 API на loopback-порту 9000; книжный Skill найден в live sandbox, его инструкция ссылается на `scripts/s3_delivery.py`. Новый сервис, миграция существующих Skill-бакетов и изменение их политик не требуются. Host/port подключения для процесса backend задаётся deployment-конфигурацией с учётом его network namespace; loopback хоста нельзя переносить в контейнер как готовый endpoint.

Общую приватную корзину и её политики настраивает оператор. Backend credentials имеют только права object IO; административные ключи и credentials существующих Skills не копируются в приложение или пользовательские контейнеры. Переход текущего VPS с бакетов пользователей требует [отдельного плана миграции](vps-attachment-storage-migration.md).

Загрузка объекта и запись в PostgreSQL не образуют общую транзакцию. Предлагаемый порядок: зарезервировать ID и состояние загрузки; загрузить объект с уникальным ключом; подтвердить размер/checksum; отметить готовность и привязать к сообщению. Незавершённые загрузки и осиротевшие объекты должны быть обнаруживаемы и очищаемы. Не помечать сообщение готовым к обработке, пока нужные файлы недоступны.

Дедупликация входящего события использует identity канала/привязки/сообщения/вложения. Checksum служит проверке целостности и возможному переиспользованию внутри разрешённого scope, но не даёт доступа к файлу другого пользователя.

Для готового файла backend фиксирует `storedAt` и `expiresAt = storedAt + 30 дней`. Чтение, ссылка из другого чата и пересылка не продлевают срок. Повтор идемпотентной загрузки сохраняет исходный срок; новая явная загрузка создаёт новый file ID и свой срок. Не нужен refcount, обход сообщений или отслеживание удаления отдельных чатов для принятия решения об очистке.

По `expiresAt` backend прекращает выдавать файл и возвращает `attachment_expired`, даже если физическое удаление из S3 ещё не завершилось. В истории остаются ID/имя и явная недоступность с предложением прислать файл заново; запрос к модели не должен молча терять изображение. Очистка удаляет объекты по времени с повтором при сбое; bucket lifecycle может служить страховкой после проверки на существующей версии MinIO, но не считается точным таймером доступа.

Системные рабочие копии и временные производные файлы не становятся обходом TTL: разрешение attachment ID проверяет срок и при наличии локального cache. Созданный и явно сохранённый исходящий документ имеет свой 30-дневный срок. TTL файлов не удаляет текст переписки и уже сохранённые расшифровки. Полное удаление данных пользователя обрабатывается отдельно и не ждёт истечения TTL.

### 4.3. Файловый доступ

Входной путь: `TG/VK → S3 → sandbox только при необходимости`. Выходной: `готовые байты или sandbox-файл → S3 → TG/VK`.

- Если модель принимает изображение без локального файла, backend готовит запрос из S3 без постоянной локальной копии.
- Инструментам, которым нужен путь, выдаётся рабочая копия через существующий sandbox resolver и `ToolInvocationMeta`.
- Для больших файлов при необходимости расширяется **тот же** `SandboxFileSystem` потоковой записью с лимитом. Новый набор обходных host IO-операций не создаётся.
- Существующий Docker-адаптер использует файловую систему хоста через mounts. Этот план не обещает нулевой host IO и не меняет данную архитектуру.
- Scratch-файлы библиотек остаются в существующих разрешённых scratch-механизмах. Источник сохранности — S3, а не scratch или контейнер.
- Публикация результата должна фиксировать завершённый файл и checksum; конкурентное изменение рабочей копии не должно приводить к расхождению метаданных и загруженных байтов.

### 4.4. Агент, LLM и результаты Skills

Предлагается расширить вход и результат выполнения структурированными ссылками на вложения, сохранив совместимый текстовый путь. При сообщении без текста наличие доступного вложения считается содержимым; текст вопроса или подпись не подменяются служебной строкой с путями.

Нужно провести ссылки через начальный ход, существующий механизм active-run input, историю, сохранение сессии и восстановление. Сам по себе этот пункт не добавляет Telegram/VK новую модель управления конкурентными ходами и не расширяет WS.

LLM получает provider-neutral content parts. Преобразование в формат провайдера выполняется перед запросом. Перенос старых `attachments: List<String>` должен сохранить читаемость сохранённых сессий и существующих пользователей адаптеров. Нельзя просто изменить смысл прежнего поля без миграционной стратегии.

Для исходящего файла агент явно выбирает результат для ответа. Рабочее название операции — «прикрепить результат»; она проверяет ownership, существование и готовность файла, сохраняет его в S3 при необходимости и добавляет ссылку к результату выполнения. Она не отправляет файл сама и не интерпретирует произвольные пути из финального текста. Отправка в другой канал остаётся явной операцией channel delivery.

Composite-команды и субагенты возвращают файловые ссылки вместе с текстовым результатом, не пересылая бинарные данные через stdout. Передача ссылки не расширяет разрешения дочернего выполнения. Knowledge продолжает хранить текст; реестр файлов и ссылки на них живут отдельно. Сжатие истории сохраняет структурированный перечень релевантных вложений и не полагается только на упоминание пути моделью.

### 4.5. Границы модальностей

| Возможность | Решение первой реализации |
| --- | --- |
| Vision | Прямой ввод изображений основной модели. Приоритет: фактический маршрут Sol, Codex-адаптер и OpenAI-compatible. Проверка capabilities относится к модели/подключению, а не только провайдеру. |
| Отдельная vision-модель | Один необязательный настроенный маршрут. Используется при явно неподдерживаемом image-входе основной модели, передаёт ей текстовый результат анализа. Не является автоматическим fallback при сетевых/auth/rate-limit ошибках. |
| Повторный просмотр | `ViewImage` сохраняется для анализа файлов, повторного вопроса, кропов и изображений страниц. |
| TXT/MD | Существующее чтение текста; ограниченные фрагменты для больших файлов. |
| HTML | Для смыслового чтения — извлечение читаемого содержимого и ссылок; для редактирования — исходная разметка. Активное содержимое не исполняется при обычном извлечении. |
| PDF | Извлечение текста по страницам; рендер выбранных страниц и OCR/vision для сканов, схем и визуальных элементов. Полный большой PDF не превращается автоматически в image-контекст. |
| QR | Специализированное декодирование; точное содержимое не заменяется догадкой vision-модели. |
| STT | Автоматическая транскрипция голосовых перед основным ходом через отдельное OpenAI Audio API подключение по 4.9; нормализация файловых кодеков при необходимости. Подпись, оригинал и транскрипт сохраняются раздельно. Пустой/ошибочный транскрипт не считается успешным распознаванием. |
| TTS | Текст → локальный HTTP API Orion → сохранённый аудиофайл → формат/представление канала. По умолчанию запрашивается native Ogg/Opus. Без переключения на другой TTS-провайдер. Повтор доставки не запускает синтез снова. |
| Генерация изображения | Sol вызывает `GenerateImage`; backend использует существующий OpenAI gateway с отдельной media-конфигурацией по 4.9, сохраняет результат в S3 и прикрепляет. Vision у Sol не означает наличие image generation у того же подключения. |
| Создание HTML/MD | Модель формирует содержимое, файловый инструмент сохраняет. HTML по возможности самодостаточен; внутренние sandbox-пути не становятся пользовательскими ссылками. |
| Создание PDF | Skill с проверяемыми зависимостями и рендером; результат прикрепляется общим способом. |

Не требуется принудительно переносить STT/TTS/image generation в chat API. Их конфигурация, credentials, лимиты и учёт вызовов должны быть явными, с использованием существующего управления HTTP-клиентами.

### 4.6. Каналы и доставка

Общий результат канала должен включать текст и упорядоченные вложения. Отсутствие текста допустимо при наличии вложения. Канал сообщает поддерживаемые виды отправки; это не универсальный реестр capabilities всех компонентов.

- Telegram: photo/document/voice/audio, подписи, выбор представления фото, группировка альбомов с ограниченным ожиданием и сохранением порядка. Проверка привязки выполняется до скачивания. Служебные сообщения привязки сохраняют прежние правила.
- VK: разбор вложений входящего сообщения, получение разрешённых URL/идентификаторов и собственная процедура upload/save/send. Семантику voice-представления и ограничения проверяют через используемый API и реальный клиент.
- Нормальный ответ бота и `SendMessageToChannel` используют одинаковые правила разрешения файлов и учёта доставки.
- `public_client` остаётся текстовым. Запрос отправить туда вложение возвращает явную неподдерживаемую возможность до частичных побочных эффектов, а не молча теряет файл.
- Пересылка между TG/VK требует проверки пользователя и целевого чата. Наличие файлов в общей корзине не означает доступа другого пользователя или автоматической передачи во все чаты.
- Форматирование текста канала и отправка HTML как файла — разные операции. Сгенерированный HTML не подставляется безусловно в Telegram/VK formatting API.

Состояние генерации отделяется от состояния доставки. Сохраняются известные результаты отдельных частей: текст, файл, внешний message ID/handle при наличии. При сбое повтор использует сохранённые S3-объекты. Сетевой timeout после внешней отправки может оставлять неопределённый результат; план не обещает exactly-once доставку там, где внешний API не позволяет её обеспечить.

Существующие lease fencing, checkpoint ordering и idempotency polling сохраняются. S3-upload, обработка и доставка не должны обходить проверку владельца выполнения или поглощать coroutine cancellation.

### 4.7. Ограничения и наблюдаемость

- Лимиты числа вложений, байтов, пикселей, страниц, длительности аудио, времени обработки и суммарного контекста задаются явно. Учитываются как channel limits, так и наши ресурсные бюджеты.
- Имя/расширение/MIME канала считаются подсказками; тип проверяется по содержимому. Имена файлов не определяют объектный ключ или произвольный путь записи.
- Получение внешних файлов учитывает допустимые источники и redirect-поведение; Telegram URL с bot token не попадает в модель, историю или логи.
- HTML/документы и извлечённый из них текст остаются недоверенными данными. Обработка не выдаёт им привилегий системных инструкций и не исполняет их код автоматически.
- Парсинг, рендер и конвертация ограничиваются временем/ресурсами и используют существующие sandbox/scratch-механизмы.
- В метрики входят стадия, длительность, размер, provider usage, ошибки и повторы; в обычные логи не помещаются бинарные payload, credentials и временные секретные URL.
- Ошибки различают неполученный файл, неподдерживаемый тип, отсутствие capability, ошибку обработки и ошибку доставки. Частичный результат сообщается явно.

### 4.8. Принятый контракт TTS Orion

Контракт проверен по документации и исходникам соседнего репозитория `orion-emulator`: `docs/tts-api.md`, `src/main/kotlin/ru/souz/orion/tts/SpeechRoutes.kt` и `SpeechService.kt`. Пользователь выбрал этот API по использованию с OpenClaw; менять конфигурацию OpenClaw или эмулятор для данного этапа не требуется.

| Параметр | Решение |
| --- | --- |
| Endpoint | Отдельный loopback listener Orion: `POST http://127.0.0.1:8092/v1/audio/speech` в текущем VPS-развёртывании. Base URL задаётся в backend-конфигурации. |
| Сеть и доступ | Вызов выполняет backend на том же хосте, не пользовательский sandbox. API не требует auth header и принимает только loopback без forwarded headers; не публиковать его через nginx и не считать `127.0.0.1` внутри другого контейнера адресом хоста. Для иного deployment доступ проектируется отдельно с сохранением изоляции. |
| Запрос | JSON: `model: "orion-tts"`, `input`, `voice`, `response_format: "opus"`. Начальный configurable voice — `joy`; доступны `sber`, `afina` и alias `eva`. |
| Текст | Непустой, до 4000 UTF-16 code units; размер всего JSON body до 64 KiB. Лимит проверяется до HTTP-вызова. |
| Опциональные поля | Не отправлять expressive instructions, SSE или изменение скорости; поддерживается только `speed=1`, `stream_format=audio`. |
| Ответ | Buffered raw audio. `opus` — Ogg/Opus (`audio/ogg`), альтернативы `mp3` (`audio/mpeg`) и `wav` (`audio/wav`). Для исходящего voice сначала использовать Opus без повторной конвертации. |
| Сохранение | Полученные байты сохраняются в S3 на 30 дней с MIME и размером. Доставка и повтор доставки используют этот объект. Заголовок API `Cache-Control: no-store` не трактуется как запрет на явно запрошенное создание пользовательского аудиофайла. |
| Конкурентность | Эмулятор выполняет один синтез за раз; конкурирующие клиенты, включая OpenClaw, могут получить 429 `tts_busy`. Союз ограничивает свои одновременные вызовы и использует только ограниченное ожидание/retry в пределах бюджета выполнения. |
| Deadline | Эмулятор ограничивает синтез с внутренним retry/конвертацией 65 секундами; клиентский request deadline — 75 секунд, но не больше оставшегося execution budget. Не дублировать внутренние retry бесконтрольными внешними повторами. |
| Ошибки | 400/413/415 — контракт/размер; 429 — занято; 503 `tts_device_unavailable` — нет подходящего cached context; 502 — upstream/format/conversion failure; 504 — timeout. Ошибка не считается созданным или отправленным голосовым. |

Эмулятор использует авторизацию, пассивно полученную из обычного трафика устройства, и держит её в памяти. Контекст переживает закрытие соединения устройства, но не restart эмулятора. Союз не получает эти credentials, не обновляет их и **не будит физическую колонку** для подготовки TTS или восстановления после ошибки. Текст и результат TTS не отправляются на колонку.

Read-only проверка `GET /health` на VPS при подготовке proposal вернула `503 waiting_for_device` и поддерживаемые model/voices/formats. Это подтверждает наличие API, но не успешный синтез. Health 200 означает наличие cached context, а не гарантию валидности upstream-авторизации. Синтез для проверки не запускался; успешный запрос после обычного появления контекста остаётся smoke-критерием этапа 5.

### 4.9. Приоритет CODEX и специализированные media API

Основная Sol через CODEX выполняет рассуждение, анализ входящих изображений, подготовку HTML/MD и содержимого PDF, вызывает инструменты и использует транскрипты. Для vision требуется добавить typed image input в существующий Codex-адаптер и проверить реальный маршрут. Отдельный vision-провайдер не обязателен для старта.

Проверка кода показывает, что `CodexChatAPI` обращается к `https://chatgpt.com/backend-api/codex/responses`, передаёт пользовательское сообщение строкой и объявляет только function tools. Собственного STT или обработчика результата hosted image generation в нём нет. Наличие инструмента генерации картинок или голосового режима в приложении Codex не доказывает доступность этих сервисов через данный адаптер.

[Документация Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) для маршрута ChatGPT plan через `api.openai.com/v1` разрешает изображения при поддержке моделью, но исключает transcription API и hosted image generation. Это другой маршрут, поэтому его ограничения не выдаются за исчерпывающую спецификацию `backend-api/codex/responses`. Подтверждённого media-контракта для текущего CODEX-подключения Союза нет; план первой поставки не зависит от его обнаружения.

В пределах разрешения использовать внешние API выбрана следующая стартовая схема:

| Назначение | Подключение первой поставки |
| --- | --- |
| Основной агент и vision | Выбранная Sol через CODEX; основную модель не заменять ради отдельной media-операции. |
| STT | OpenAI `POST /v1/audio/transcriptions`, модель `gpt-transcribe`, buffered JSON с текстом. Переиспользовать `OpenAIVoiceAPI` и его обработку языкового параметра этой модели; backend явно задаёт модель вместо неявного default. |
| Генерация картинки | Sol вызывает существующий `GenerateImage`, исполняемый через `OpenAIImageGenerationGateway` и `POST /v1/images/generations`. Стартовая модель `gpt-image-2.5-flare`, одна PNG 1024×1024, quality `medium`; параметры конфигурируемы. Сохранение/доставка выполняются общим файловым потоком. |
| TTS | Orion по 4.8; выбор media API не меняет решение о локальном TTS endpoint. |

Выбор моделей опирается на официальные руководства [по транскрипции](https://developers.openai.com/api/docs/guides/transcription) и [генерации изображений](https://developers.openai.com/api/docs/guides/image-generation). Это стартовые настройки предлагаемой реализации, не утверждение об их доступности в текущем deployment. Проверка совместимости request/response и доступа к модели обязательна до включения.

Для STT и image generation backend получает явно заданные endpoint, model, credential reference и timeout. На старте это OpenAI API с отдельным Platform API-доступом и его учётом расходов; OAuth-токен CODEX не подставляется вместо API key. Обе media-операции могут использовать один разрешённый Platform credential, но не наследуют его из выбранной chat-модели. Секреты остаются в backend и не передаются модели или sandbox. Новая система универсального выбора провайдеров не нужна: достаточно конфигурации существующих адаптеров и composition root.

При отсутствии настроенного доступа capability явно недоступна. Ошибки credentials, квоты или сети не вызывают автоматического переключения на иной сервис. В дальнейшем подтверждённая CODEX media-интеграция может заменить исполнителя существующей операции; её исследование не блокирует первую поставку и не требует заранее создавать отдельный framework. Самостоятельное размещение STT/image-моделей, запуск Codex CLI как вложенного агента и автоматизация интерфейса Codex в первую поставку не входят.

| Модуль | Изменения |

Новые production project dependencies не планируются. S3 SDK, если выбран, является библиотечной зависимостью backend. Не создавать отдельный универсальный media framework; расширять существующие точки композиции.

## 6. Этапы реализации

### Этап 0. Решения по контрактам и совместимости — закрыт

**Модули:** `:llms`, `:agent`, `:backend`, `:sharedLogic`. **Зависимости:** нет.

- Принята стартовая техническая основа раздела 8: минимальные внутренние типы, additive-миграция, две файловые операции, набор инструментов и конфигурируемые ограничения.
- Зафиксированы существующий MinIO, TTL файлов 30 дней без refcount, очистка незавершённых загрузок через 24 часа и готовый HTTP TTS Orion. Внешние API разрешены с приоритетом CODEX; стартовый media routing определён в 4.9.
- Отделить решения, необходимые для написания кода, от конфигурации и live-проверок перед включением. Credentials и фактические production endpoints не требуются для фиксации интерфейсов.
- Реальную передачу изображения через Sol проверить на этапе 4 после реализации адаптера. Этап 0 определяет маршрут и критерий проверки, но не утверждает, что smoke уже выполнен.

**Готовность:** достигнута для проектирования. Решения и стартовые параметры зафиксированы, открытых вопросов к владельцу для начала реализации нет. Параметры конкретного развёртывания имеют явную конфигурационную границу; WS колонок не требует изменения. Live-проверки после реализации остаются обязательными критериями приёмки. Реализация этапов 1–7 ведётся; закрытие этапа 8 требует общей регрессионной проверки и live-приёмки подключений.

### Этап 1. S3 и мост к существующему sandbox

**Модули:** `:backend`, `:sharedLogic`. **Зависимости:** этап 0.

- Реализовать owner-scoped доступ к операторской общей корзине и app-owned lifecycle S3-клиента.
- Добавить файловые записи, состояния загрузки, готовность объекта, привязку к владельцу и процедуры восстановления незавершённых операций.
- Реализовать сохранение/чтение байтов и потоков с лимитами/checksum, без постоянного локального зеркала.
- Реализовать материализацию рабочей копии и сохранение завершённого sandbox-файла через имеющийся resolver; добавить потоковую запись в существующий интерфейс только при необходимости.
- Реализовать 30-дневный TTL готовых объектов и `attachment_expired` без анализа ссылок из чатов. Незавершённые загрузки очищаются отдельно; принятый технический срок — 24 часа.

**Проверки:** два пользователя в одной приватной корзине; запрещённый чужой ID; повтор идемпотентного upload; сбой между S3 и PostgreSQL в обе стороны; оборванный поток; слишком большой файл; восстановление после удаления рабочей копии/пересоздания контейнера; истечение 30 дней при сохранённом чате; неизменность срока после пересылки; просроченная рабочая копия; повтор удаления при недоступном S3.

**Готовность:** сохранённый файл читается без исходного контейнера; новые host mounts и обходной host IO не требуются.

### Этап 2. Вложения в сообщениях, агенте и файловых результатах

**Модули:** `:llms`, `:agent`, `:sharedLogic`, `:backend`; compatibility-only изменения других consumers при необходимости. **Зависимости:** этап 1.

- Добавить связи файлов с сообщениями и передать их через turn request, initial/active-run input, session persistence и outcome.

Для изменения только этого proposal достаточно проверки локальных ссылок и `git diff --check`; runtime-тесты не требуются.

При реализации выполнять команды из актуальных module AGENTS.md, включая:

```sh

./gradlew test :sharedLogic:allTests :sharedUI:allTests :koverXmlReport :koverHtmlReport koverLog -Psouz.coverage --no-parallel
```

Backend-тестам требуется Docker. При изменении sandbox дополнительно собрать образ и выполнить opt-in Docker tests по [инструкциям модуля](../../sharedLogic/AGENTS.md). Для общих DTO включить проверки затронутых consumers; repository-wide `check` выполнить, когда масштаб изменения это требует. Команды coverage и ratchet относятся к реализации, а не к текущему documentation-only изменению.

Интеграционные тесты S3 должны проверять реальный протокол через тестовый S3-compatible сервис, а не только mock интерфейса. Его provisioning/permissions дополнительно проверяются на выбранном целевом провайдере. Fixtures не должны требовать production credentials. Внешние TG/VK/model проверки — отдельный управляемый smoke-набор.

Обязательная сквозная матрица:

| Группа | Критерий |
| --- | --- |
| Пользовательский результат | Каждый заявленный входной/выходной формат проходит через TG и VK; файл доступен пользователю, а не только существует в sandbox. |
| Сохранность и TTL | В пределах 30 дней после перезапуска runtime и пересоздания контейнера доступен оригинал и точная ранее отправленная версия. После срока — явный `attachment_expired`, независимо от ссылок в чатах и наличия cache. |
| Совместимость | Старые text-only сессии читаются; публичный WS-контракт колонок остаётся текстовым. |
| Изоляция | Чужие file IDs, bucket/key, traversal и ссылки вне разрешённого scope не дают доступа; явная пересылка проверяет целевой канал. |
| Повторы | Повтор входящего события не создаёт лишний ход/объект; retry доставки использует готовый результат. Неопределённый внешний receipt не выдаётся за гарантированную доставку. |
| Частичные сбои | Ошибки S3, DB, провайдера и канала различимы; успешно отправленные части учитываются; незавершённые загрузки не маскируются готовыми. |
| Ресурсы | Размер, пиксели, страницы, длительность, memory/context budgets, timeout и cancellation проверяются реальными файлами и процессами. |
| Skills | Файл не теряется через composite/subagent/Knowledge-offload/summarization; обработка не расширяет разрешённый каталог инструментов. |

## 8. Решения этапа 0: принятая стартовая основа

**Статус раздела:** пользователь принял техническую основу как стартовые решения. Этап 0 закрыт; документ остаётся PROPOSED для целевого объёма; реализованная часть описана отдельно в runtime guide. Подтверждены существующий MinIO, TTL 30 дней без подсчёта ссылок, готовый HTTP TTS Orion и допустимость внешних API с приоритетом CODEX. Стартовые STT/image-generation подключения определены в 4.9; live-доступ к ним не проверялся. Orion API обнаружен на VPS, live-синтез не проверялся.

### 8.1. Минимальные контракты и операции

Сохранить `content: String` и `output: String`, добавив структурированные поля с пустыми значениями по умолчанию. Не переводить весь граф на новый универсальный формат сообщений и не создавать абстракцию для ещё не поддерживаемых модальностей.

| Контракт | Содержание и владелец |
| --- | --- |
| `FileReference` | Стабильный непрозрачный `fileId` в `:llms`. Без bucket/key, URL, credentials и host path; общий тип может использоваться в LLM-истории и контракте агента без новых project dependencies. |
| `ImageContent` | `FileReference` и запрошенный режим детализации в `:llms`. Для нового пути сообщения сохраняются текст и упорядоченный список изображений. Провайдер разрешает файл перед отправкой, а не читает S3 сам. |
| `MessageAttachment` | Ссылка, имя, MIME, размер и способ показа в `:agent`; backend проверяет метаданные, а не доверяет значениям модели. Ссылки проходят через вход/выход выполнения и инструменты. |
| `StoredFile` и связи | Backend-запись с владельцем, ключом объекта, checksum, состоянием готовности и происхождением; отдельные связи с сообщениями и выполнением. PostgreSQL остаётся источником прав доступа. |
| Host-доступ к вложению | Узкий SPI в `:agent` для подготовки рабочей копии и регистрации результата; backend реализует доступ через S3 и существующий sandbox resolver. Binary resolution для LLM связывается через runtime composition в `:sharedLogic`. |

Новые typed image parts не переиспользуют поле `attachments: List<String>` с изменённым смыслом. Старое поле сохраняется как legacy-путь до завершения миграции consumers. Старые provider IDs/пути не объявляются автоматически объектами S3 и не отправляются другому провайдеру без разрешения источника.

Приняты две явные compiled операции, доступные через существующую Skill-discovery и enabled-tools policy:

- **`PrepareAttachment(fileId)`** — проверяет доступ текущего выполнения, подготавливает рабочую копию в его sandbox и возвращает путь/метаданные. Повтор может переиспользовать неизменившуюся копию. Входящие изображения для прямого LLM-запроса не обязаны проходить эту операцию.
- **`AttachFileToReply(path | fileId, presentation)`** — принимает ровно один источник, проверяет доступ, при необходимости сохраняет завершённый файл в S3 и включает ссылку в результат текущего выполнения. Сама операция не отправляет сообщение во внешний канал. Повторный выбор того же файла не добавляет дубликат.

`AttachFileToReply` в субагенте возвращает выбранные файлы родителю; только родитель выбирает, какие включить в пользовательский ответ. Не нужен отдельный публичный инструмент «загрузить в S3» или автоматическое сканирование рабочего каталога. `SendMessageToChannel` принимает сохранённые `fileId` и необязательный текст, проверяет возможность доставки всего запроса до начала отправки и сохраняет явную адресацию канала.

Миграция: additive PostgreSQL-таблицы/поля; новая версия agent session читает текущую v1, отсутствующие списки считает пустыми, неизвестную будущую версию отклоняет явно. Запись нового формата включается только после обновления всех backend workers. Первое включение выполняется с остановкой приёма новых ходов и завершением либо явной отменой активных; работа старого writer с новой сессией не поддерживается. Отключение feature не удаляет новые поля/файлы. Возврат на старый бинарник после записи нового формата требует отдельного плана совместимости, а не автоматического удаления вложений.

### 8.2. Стартовый технический набор

| Область | Стартовое решение |
| --- | --- |
| S3-клиент | AWS SDK for Java v2 только в `:backend`; подключение к существующему MinIO, app-owned client, явные `endpoint`, signing `region`, `pathStyleAccess`, credential source и namespace бакетов. Совместимость SDK с установленной версией MinIO проверяется интеграционно; обновление самого MinIO не подразумевается. |
| Создание бакета | Лениво при первом входящем или исходящем сохраняемом файле. Сначала в DB фиксируется непрозрачный storage ID и имя, затем идемпотентно выполняется provisioning; параллельные запросы используют одну запись. Имя: административный installation prefix плюс случайный UUID без дефисов, без пользовательского имени. |
| Объекты | Уникальный ключ `files/<fileId>`; оригинальное имя — метаданные. Для первой версии при ограничении размера достаточно одиночного PUT; multipart upload и межпользовательская дедупликация не нужны. Проверка целостности — собственный SHA-256 и размер, не предположение о значении ETag. |
| Конфигурация хранения | Backend service credentials приходят из конфигурации окружения/secret injection; они не передаются в контейнер пользователя. Выбор конкретного S3-сервиса не меняет внутренние DTO. |
| Retention — принято | Готовый объект доступен 30 дней от `storedAt`; ссылки/чтение/пересылка не меняют `expiresAt`. Backend проверяет срок, очистка удаляет по времени; готовность объекта после срока не определяется успешным HEAD. Срок очистки незавершённых загрузок — 24 часа. |
| TTS — принято | HTTP API эмулятора Orion, модель `orion-tts`, Opus, default voice `joy`. Локальный endpoint использует Sber upstream внутри эмулятора; Союз не дублирует этот клиент и не переключается на `GigaVoiceAPI.synthesize`. Новая модель и hardware budget не нужны. |
| STT / image generation | Отдельные OpenAI Audio/Images API подключения на базе существующих адаптеров по 4.9. CODEX остаётся основным chat/vision route и вызывает media tools; его OAuth не используется как Platform API key. |
| Основная модель | Использовать выбранный для выполнения маршрут `(provider, connectionId, modelId)` без отдельного жёстко заданного имени Sol. Явный признак image input хранится в настройке маршрута. Включение подтверждённого маршрута зависит от image smoke на этапе 4. |
| Отдельная vision-модель | Необязательная ссылка на уже конфигурируемый маршрут модели. Применяется только при отсутствии image capability у основного маршрута; credentials разрешаются для выбранного vision route. Настройки основного агента не мутируются. При отсутствии обоих путей — явная ошибка capability. |
| PDF generation | File-backed Skill создаёт HTML/CSS и вызывает WeasyPrint в sandbox. Он использует встроенные/подготовленные ресурсы, разрешённые шрифты и ограниченный resource loader; произвольный network fetch при рендере не требуется. Основания выбора: [настройка S3 endpoint в AWS SDK](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/endpoint-config.html), [WeasyPrint: HTML/CSS → PDF](https://doc.courtbouillon.org/weasyprint/stable/), [ограничения обработки недоверенного HTML](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html#security), [Tesseract](https://tesseract-ocr.github.io/tessdoc/), [ZXing](https://github.com/zxing/zxing). Это выбор технических инструментов, а не утверждение об их наличии в текущем runtime.

### 8.3. Принятые стартовые ограничения

Все значения конфигурируемы. Они являются ограничениями Союза, а не обещанием, что любой внешний провайдер принимает такой объём. Эффективный лимит — минимум продуктового, транспортного и provider-specific лимита. Неподдерживаемый объём отклоняется явно; отсутствие доступного провайдера не маскируется усечением данных.

| Ограничение | Стартовое значение |
| --- | --- |
| Один входящий/исходящий файл | 20 000 000 байт; размер известного файла проверять до скачивания, поток ограничивать независимо от заголовка. |
| Одно логическое сообщение | До 10 файлов и 100 000 000 байт суммарно. |
| Изображение для декодирования | До 40 млн пикселей и 16 384 пикселей по любой стороне; оригинал не уменьшать при сохранении. |
| Изображения в одном model request | До 5; остальные доступны по ссылкам для последующих запросов. Рабочая копия для первичного просмотра — длинная сторона до 2048 px; для мелкого текста — отдельные кропы/детальный просмотр. |
| PDF | До 500 страниц; один текстовый запрос — до 10 страниц и 50 000 символов, один рендер/OCR-вызов — до 5 страниц с общим pixel budget. |
| Входящее аудио | До 10 минут и файлового лимита. Если выбранный STT принимает меньше, действует его предел; скрытая обрезка запрещена. Автоматическая сегментация длинных записей не обязательна для первой версии. |
| TTS одного запроса | До 4000 UTF-16 code units и 64 KiB всего JSON согласно Orion API; превышение требует явного сокращения или разделения агентом, без молчаливого усечения. |
| Album collection TG | Завершение после 1,5 с без нового элемента; абсолютное ожидание не более 5 с. Поздние элементы обрабатываются отдельным продолжением с сохранением group identity, без перезапуска завершённого хода. |
| Файловый transfer | Общий deadline 120 с на попытку; retry ограничен общим бюджетом операции. |
| Одна конвертация/OCR/PDF-render job | Deadline 120 с; существующая отмена останавливает дочерние процессы. |

| Конкурентная тяжёлая подготовка | Одна job на пользователя; process-wide предел задаётся deployment. Ожидание не удерживает DB transaction или polling processing permit без необходимости. |

Объём model input дополнительно ограничивается context budget выбранного маршрута. Текстовый подсчёт не выдаётся за точную стоимость изображения: учитывать provider usage и ограничивать число/размер изображений до отправки. Без отдельной оценки не заявлять точный image token count.

### 8.4. Итог согласования

| Вопрос | Зафиксированное решение |
| --- | --- |
| S3-сервис | Использовать уже поднятый локальный S3, применяемый в Skills. Read-only проверка подтвердила работающий MinIO на VPS. Подключение backend и выделенные credentials — параметры развёртывания; политика старых бакетов не наследуется. |
| Retention | На старте хранить 30 дней; отказ от расчёта срока через удаление сообщений и число ссылок. Предложение «до удаления последней ссылки плюс 7 дней» снято. |
| TTS | Выбран существующий Orion `POST /v1/audio/speech`. Контракт проверен по исходникам; loopback health на VPS доступен и сообщает `waiting_for_device`. Выбор модели/сервиса закрыт; успешный live-синтез — проверка перед включением. |
| STT и image generation | Внешние API допустимы; предпочтение — CODEX. Для первой поставки выбраны существующие OpenAI media-адаптеры с отдельным API-доступом по 4.9, поскольку media-контракт текущего CODEX route не подтверждён. Основная Sol сохраняет vision и управление инструментами. |
| Остальная техника | Минимальные операции/DTO из 8.1, инструменты из 8.2, срок незавершённых загрузок 24 часа и стартовые лимиты из 8.3 приняты пользователем. |

Открытых продуктовых или архитектурных вопросов этапа 0 не осталось. Реализацию можно начинать по этапам 1–8 после отдельного поручения. Endpoint/credentials, доступность выбранных media-моделей и фактическая работа Sol vision относятся к конфигурации и проверкам перед включением. Их отсутствие не означает необходимости пересогласовывать файловые контракты, но не позволяет включить соответствующую capability.

### 8.5. Проверки перед включением, не являющиеся открытыми решениями дизайна

- Provisioning, доступ и удаление в фактическом S3-сервисе; квоты бакетов и ожидаемый объём хранения.
- Реальный image request через основной Sol route и отдельный vision route, если настроен.
- STT/image generation через выбранные credentials и реальные ограничения этих сервисов; Orion TTS — успешный синтез при доступном cached context без пробуждения колонки и без передачи его credentials Союзу.
- Отображение photo/document/voice в TG и VK; поведение сетевых повторов и частичных отправок.
- Совместимость версий в собранном sandbox image, шрифты, OCR-fixtures и визуальная проверка PDF.

До прохождения этих проверок можно реализовывать и тестировать согласованный план, но нельзя объявлять capability готовой в целевом развёртывании.
